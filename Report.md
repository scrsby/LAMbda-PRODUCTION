# Static Code Analysis Report — LAMbda-PRODUCTION

**Scope:** Full repository static review — server (Express/TypeScript), client (TypeScript), database (SQL migrations + `supabase_dump.sql`), dependencies (`package.json`/`package-lock.json`), and container configuration (`Dockerfile`/`docker-compose.yml`).

**Method:** Manual code review of authentication, session, and routing logic, supplemented by targeted analysis of client-side rendering, SQL schema, and infrastructure configuration. All findings below were traced to specific files/lines; most were independently verified against the source.

**Severity scale:** Critical > High > Medium > Low.

---

## Summary of Highest-Priority Findings

| # | Severity | Area | Finding |
|---|---|---|---|

## 1. Server — Authentication & Access Control

### 1.1 `server/routes/admin.ts:94-125` — `GET /admin/getAllAccessTokens` is completely unauthenticated
- **Description:** Unlike every other route in `admin.ts`, this endpoint has no `requireAuth`/`requireUserType` middleware. It returns every access token record: `email`, `access_token` (the exact numeric token consumed by `POST /auth/createAccount`), `created_by`, `created_at`, `expires_at`, and status.
- **Impact:** Any unauthenticated attacker can harvest live invite tokens — including for `vendor-admin`/`system-admin` invites — and race the legitimate recipient to create a privileged account.
- **OWASP:** A01:2021 – Broken Access Control
- **Severity:** Critical
- **Fix:** Add `requireAuth, requireUserType('system-admin', 'vendor-admin')` (matching the sibling routes) to this route.

### 1.2 `server/routes/auth.ts:262-349` and `134-260` — No rate limiting on `/login` and `/createAccount`
- **Description:** `forgotPasswordRateLimit`/`resetPasswordRateLimit` are applied to the password-reset routes, but `/login` and `/createAccount` have no rate-limit middleware at all.
- **Impact:** `/login` is brute-forceable for credential stuffing. `/createAccount` is more severe: it accepts an `accessToken` integer generated by `randomInt(100000, 1000000)` (`admin.ts:20-22`, ~900,000 possible values) with a 7-day validity window and no attempt limiting, making it brute-forceable well within that window if an attacker knows a target's email.
- **OWASP:** A07:2021 – Identification and Authentication Failures
- **Severity:** High
- **Fix:** Apply an IP/email-scoped rate limiter to both routes; consider increasing token entropy (e.g., use `randomBytes` and hash-compare, as already done for password-reset tokens at `auth.ts:493-495`).

### 1.3 `server/routes/admin.ts` — Role-only authorization without ownership scoping (IDOR)
- **Routes affected:** `GET /getUsers` (347), `GET /getVendors` (392), `POST /createVendor` (410), `GET /discounts` (439), `POST /discounts` (454), `DELETE /discounts/:discountId` (504), `DELETE /deleteVendor/:vendorId` (531), `GET /sales` (562).
- **Description:** `requireUserType('system-admin', 'vendor-admin', ...)` only checks the caller's role, never that a `vendor-admin` is restricted to their own `vendor_id`. Contrast with `server/routes/vendor.ts:26-27` and `server/routes/inventory.ts:251-363`, which correctly derive `vendorId` exclusively from `req.session.user.vendorId`.
- **Impact:** Any `vendor-admin` account can list all users/vendors platform-wide (including other vendors' staff PII), create/delete any vendor, manage any vendor's discounts, and view the full-platform sales/commission report.
- **OWASP:** A01:2021 – Broken Access Control (IDOR)
- **Severity:** High
- **Fix:** Add a `WHERE vendor_id = $session.vendorId` scoping clause (or an explicit ownership check) for all `vendor-admin`-accessible routes, mirroring the pattern already used in `vendor.ts`/`inventory.ts`.

### 1.4 `server/routes/inventory.ts:34-51, 57-143` — `/all` and `/search` expose all vendors' inventory
- **Description:** Both routes allow `vendor`, `vendor-employee`, and `vendor-admin` roles (not just admins) with no `vendor_id` filter tied to the caller's session.
- **Impact:** Any vendor employee can enumerate competitors' full inventory (names, prices, quantities).
- **OWASP:** A01:2021 – Broken Access Control (IDOR)
- **Severity:** High
- **Fix:** Restrict `/all` to admin-only roles, or scope by session `vendorId` like the sibling `/vendor/items` and `/vendor/search` routes.

### 1.5 `server/routes/inventory.ts:150-245 (`/add`), 526-554 (`/remove-item`)`
- **Description:** These admin routes accept a client-supplied `vendorId`/item ID with only role-based checks — a `vendor-admin` can add inventory to, or delete inventory from, a vendor they don't manage.
- **OWASP:** A01:2021 – Broken Access Control
- **Severity:** Medium
- **Fix:** Verify the caller's `vendor-admin` scope matches the target `vendorId` before mutating, or restrict these mutating routes to `system-admin`/`admin` only.

### 1.6 `server/routes/POS.ts:230-262` — Client-trusted pricing on `/update-ticket`
- **Description:** `final_price`, `vendor_price`, `discount_amount`, and derived `commission`/`payout` (10%/90% split) are taken directly from `req.body` and persisted without recomputation from the authoritative `inventory` price/discount data.
- **Impact:** A malicious or compromised cashier/employee session can submit an arbitrary low `final_price`, causing under-charging and incorrect vendor payouts/commission.
- **OWASP:** A04:2021 – Insecure Design
- **Severity:** High
- **Fix:** Recompute price, discount, commission, and payout server-side from trusted inventory/discount records; treat client-submitted amounts as untrusted display data only.

### 1.7 `server/routes/POS.ts` — Router-level auth applied globally, not per-route
- **Description:** Several routes (`/inventory-search`, `/ticket/:id` GET, `/tickets`, `/receipts`, `/receipt/:id`, `/vendors`) have no inline `requireAuth`, relying entirely on a `router.use(requireAuth, requireUserType(...), posRouteRateLimit)` applied earlier in the file (line ~150). Functionally protected today, but fragile: any future route added above that `router.use()` call, or any reordering during a refactor, would silently remove protection.
- **OWASP:** Misconfiguration (defense-in-depth gap)
- **Severity:** Low
- **Fix:** Apply auth middleware explicitly per-route as defense in depth, even though the router-level guard currently covers them.

### 1.8 `server/utils/auth-middleware.ts` — reviewed, no issues found
`requireAuth`/`requireUserType` correctly check `req.session.user` and return 401/403 appropriately. This is the correct pattern; the issue is inconsistent *application* of these functions (see 1.1–1.5), not the middleware itself.

### 2.2 `server/routes/admin.ts:129` — Logs user email on every user-creation request

- **Fix:** Mask most of the token in the UI (e.g., show last 4 digits) or require an explicit "reveal" action.

## 3. Client — Cross-Site Scripting (XSS)

### 3.1 `client/src/ts/admin/admin-user-settings.ts:126-144`
- **Description:** Table rows are built via `row.innerHTML` interpolating `name` (from user-supplied `first_name`/`last_name`), `vendorId`, `email`, `phone`, and `user_type` with no escaping. These names are set by users themselves via account finalization and stored as free text.
- **Impact:** A user who sets a malicious first/last name (e.g., `<img src=x onerror=...>`) achieves stored XSS in the browser of every system-admin who views the Users table — a privilege-escalation vector.
- **OWASP:** A03:2021 – Injection (Stored XSS)
- **Severity:** High
- **Fix:** Use `textContent` for all interpolated fields (already done correctly in `admin-discount-manager.ts:50-54`), or apply the existing `escapeHtml()` helper (already used in `admin-order-detail.ts`/`register.ts`) consistently, including to attribute values like `data-name="${name}"`.

### 3.2 `client/src/ts/admin/admin-vendor-settings.ts:151-165`, `client/src/ts/POS/orders.ts:126-136`, `client/src/ts/admin/admin-sales-manager.ts:479-489`, `client/src/ts/vendor/vendor-sales-manager.ts:352-360`
- **Description:** `ticket.employee_name` and similar DB-sourced fields interpolated into `innerHTML` without escaping (same root cause as 3.1).
- **OWASP:** A03:2021
- **Severity:** Medium-High
- **Fix:** Same as 3.1 — escape or switch to `textContent`.

### 3.3 `client/src/ts/admin/admin-inventory-settings.ts:172`, `client/src/ts/vendor/vendor-inventory.ts:160`, `client/src/ts/POS/register.ts:945-968`
- **Description:** `item.itemName` (free-text, admin/vendor-entered) rendered raw into `innerHTML`; `renderSearchResultsMessage`'s message parameter is also interpolated unescaped with no current unsafe callers but no defense in depth.
- **OWASP:** A03:2021
- **Severity:** Medium
- **Fix:** Escape `item.itemName` and treat message parameters as HTML-unsafe by default.

### 3.4 `client/src/ts/admin/admin-invite-settings.ts:142-164`
- See finding 2.4 — same unescaped-`innerHTML` pattern applies to `email`/`created_by`/`status`.

### 3.5 `client/src/ts/admin/admin-sales-manager.ts:439-445`, `client/src/ts/utilities/receipt.ts:358-364`
- **Description:** `reportWindow.document.write(reportHtml)` / `receiptWindow.document.write(receiptHtml)` write to a newly opened window. `receipt.ts` escapes header text but the escaping of interpolated row/item/vendor names feeding into this HTML should be verified end-to-end.
- **OWASP:** A03:2021
- **Severity:** Medium
- **Fix:** Ensure every dynamic value reaching these HTML strings is escaped at the interpolation point; prefer constructing DOM nodes over `document.write`.

### Positive findings (client)
- `client/src/ts/utilities/api.ts:14-45` uses `withCredentials: true` with cookie-based sessions rather than storing tokens in `localStorage` — good practice against XSS-based token theft. No hardcoded API keys/secrets were found anywhere under `client/src/ts`.

## 4. Client — Access Control / Storage

### 4.1 `client/src/ts/utilities/redirect.ts:1, 31-70`
- **Description:** `const REDIRECTS_ENABLED = false;` disables the entire client-side `requireUserType()` route guard, making it a no-op. Any authenticated user can navigate directly to admin/vendor/POS HTML pages.
- **Impact:** Purely a defense-in-depth gap as long as every server API independently re-checks `user_type` (see Section 1 for cases where that check is present but insufficiently scoped, and 1.1 where it's entirely absent) — but it removes a layer that would otherwise limit UI-level information disclosure.
- **OWASP:** A01:2021 – Broken Access Control
- **Severity:** Medium
- **Fix:** Re-enable `REDIRECTS_ENABLED` (or remove the dead flag) and continue enforcing authorization server-side regardless.

### 4.2 `client/src/ts/POS/register.ts:270, 327, 499, 1172, 1224, 1250, 1330`
- **Description:** `currentTicketId` is stored in `localStorage` rather than `sessionStorage`. Low-sensitivity value, but persists across tabs/sessions and is readable by any injected script (compounding the XSS findings in Section 3).
- **OWASP:** A05:2021 – Security Misconfiguration
- **Severity:** Low-Medium
- **Fix:** Use `sessionStorage`; ensure the server independently verifies the acting user is authorized for the referenced ticket on every request.

### 4.3 `client/src/ts/auth/create-account.ts`, `reset-password.ts`
- **Description:** Both only check `password.length < 8` on the client; the stronger `isValidPassword()` helper in `form-validation.ts` (upper/lower/digit-or-symbol) exists but is not called.
- **OWASP:** A07:2021 – Identification and Authentication Failures
- **Severity:** Low (client-side check is not a security boundary; verify server enforces an equivalent policy — currently `auth.ts:632-637` also only checks length ≥ 8)
- **Fix:** Call the shared validator consistently on the client, and add complexity requirements server-side in `auth.ts`.

## 5. Database — Schema, Data Exposure, and Performance

### 5.1 `supabase_dump.sql` (committed at repo root, ~196 KB) — Real production PII and password hashes committed to git
- **Description:** The dump contains live user rows with real emails, phone numbers, and bcrypt password hashes, e.g. (`supabase_dump.sql:4280-4283`):
  - `seannedcrosby@gmail.com`, phone `8167155135`, hash `$2b$10$YT4Ovj0j7...`
  - `lawrenceantiquemall@gmail.com`, phone `7853933230`, hash `$2b$10$AY/roqx...`
  Verified directly in the file and confirmed present in git history (`git log -- supabase_dump.sql`).
- **Impact:** If the repository is or becomes public, or any collaborator's access is compromised, attackers obtain real PII plus bcrypt hashes to attack offline.
- **OWASP:** A02:2021 – Cryptographic Failures / sensitive data in version control
- **Severity:** Critical
- **Fix:** Remove `supabase_dump.sql` from the repository and purge it from git history (e.g. `git filter-repo`/BFG); rotate the affected users' passwords; add the file pattern to `.gitignore`; use sanitized/synthetic fixtures for any future committed dumps.

### 5.2 `supabase_dump.sql:3622-3633` — `public.users.email` has no `UNIQUE` constraint
- **Description:** Only `NOT NULL` is enforced on `email`; no unique index exists in the `public` schema (only Supabase's own `auth.users` has one). Application login logic (`auth.ts:276-281`) selects by `email` alone and uses the first row, so duplicate rows would produce ambiguous authentication behavior, and nothing in the DB layer prevents `/createAccount` race conditions from creating duplicates outside the app-level check.
- **OWASP:** A07:2021 (secondary); primarily a data-integrity/Performance-Reliability issue
- **Severity:** High
- **Fix:** `ALTER TABLE public.users ADD CONSTRAINT users_email_key UNIQUE (email);` (consider a unique index on `lower(email)` for case-insensitive matching, matching how login/reset lookups are performed).

### 5.3 Missing indexes on application foreign keys (Performance/Reliability)
Verified in `supabase_dump.sql:5673-5698` and `migrations/006_create_discounts_table.sql:6` — none of the following FK columns have a supporting index:
- `public.access_tokens.created_by` → `users(user_id)`
- `public.ticket_items.ticket_id` → `tickets(ticket_id)`
- `public.tickets.cashier_id` → `users(user_id)`
- `public.users.vendor_id` → `vendors(vendor_id)`
- `public.discounts.vendor_id` → `vendors(vendor_id)`
- **Impact:** `tickets`/`ticket_items` are queried constantly by POS/admin sales pages; sequential scans will degrade badly as ticket volume grows, and `ON DELETE CASCADE` on `ticket_items` will slow down proportionally.
- **Severity:** Medium-High
- **Fix:**
  ```sql
  CREATE INDEX idx_ticket_items_ticket_id ON public.ticket_items(ticket_id);
  CREATE INDEX idx_tickets_cashier_id ON public.tickets(cashier_id);
  CREATE INDEX idx_users_vendor_id ON public.users(vendor_id);
  CREATE INDEX idx_access_tokens_created_by ON public.access_tokens(created_by);
  CREATE INDEX idx_discounts_vendor_id ON public.discounts(vendor_id);
  ```

### 5.4 `migrations/004_create_reset_password_tokens_table.sql:1-9`
- **Description:** `reset_password_token` has no `UNIQUE` constraint or index (only `email` is indexed), even though lookups are performed by token (`auth.ts:652-657`). There is also no `used`/`used_at` column, so a reset token can be replayed multiple times until it expires.
- **OWASP:** Performance/Reliability; secondarily A07:2021
- **Severity:** Medium
- **Fix:** `CREATE UNIQUE INDEX idx_reset_password_tokens_token ON public.reset_password_tokens(reset_password_token);` and add a `used_at` column, checked and set on first successful reset.

### 5.5 `supabase_dump.sql:3622-3633` — `phone bigint`
- **Description:** Storing phone numbers as `bigint` truncates leading zeros and cannot represent `+`-prefixed international formats or extensions.
- **OWASP:** Performance/Reliability (data integrity)
- **Severity:** Low
- **Fix:** Store as `TEXT` with application-level format validation.

### 5.6 `supabase_dump.sql:846, 864-865` — `pg_net` HTTP functions granted to `anon`
- **Description:** `GRANT EXECUTE ON FUNCTION net.http_get(...)/net.http_post(...) TO ... anon, authenticated, service_role;`. If any exposed RLS policy or RPC allows the unauthenticated `anon` role to reach these functions, this permits server-side HTTP requests to arbitrary URLs from within the database.
- **OWASP:** A10:2021 – Server-Side Request Forgery / A05:2021 – Security Misconfiguration
- **Severity:** Medium (Supabase default scaffolding, but a live grant in the deployed database)
- **Fix:** Revoke `EXECUTE` on `net.http_get`/`net.http_post` from `anon` unless explicitly required; restrict to `service_role`.

### 5.7 `migrations/006_create_discounts_table.sql`
- **Description:** `CHECK (end_time > start_time)` exists (good), but there's no index on `(vendor_id, start_time, end_time)` for the "currently running discounts" queries used by `register.ts`.
- **OWASP:** Performance/Reliability
- **Severity:** Low
- **Fix:** `CREATE INDEX idx_discounts_active_window ON discounts(vendor_id, start_time, end_time);`

## 6. Dependencies

### 6.1 `axios` misclassified as a devDependency (`package.json` devDependencies, locked at `1.19.0`)
- **Description:** `axios` is imported by `client/src/ts/utilities/api.ts` and bundled into the production `client/dist` webpack output, but is listed under `devDependencies` rather than `dependencies`.
- **OWASP:** A06:2021 – Vulnerable and Outdated Components (classification hygiene; confirm exact CVE exposure with an authoritative audit tool)
- **Severity:** Medium
- **Fix:** Move `axios` to `dependencies`; run a dependency-audit tool (e.g. `npm audit`) to confirm the resolved patch level is free of known CVEs, and bump if not.

### 6.2 `package.json` — `session` (`^0.1.0`) and `tsconfig` (`^7.0.0`) as production dependencies
- **Description:** `session` appears to be an old/unmaintained package unrelated to (and potentially confused with) `express-session`, which is what the app actually uses (`server/config/app.ts:23-24`). `tsconfig` is normally a dev-only convenience package, not a runtime dependency.
- **OWASP:** A06:2021 – Vulnerable and Outdated Components (unmaintained/unused dependency increases supply-chain surface)
- **Severity:** Low
- **Fix:** Remove `session` and `tsconfig` from `dependencies` if unused (verify with a repo-wide import search first).

### Positive finding
`connect-pg-simple` is used as the session store (`server/config/app.ts:54-60`) rather than the default in-memory store, which Express explicitly documents as unsafe for production.

## 7. Container / Infrastructure Configuration

### 7.1 `Dockerfile:23-51` — Production container runs as root
- **Description:** No `USER` instruction is present; the Node process runs as root inside the container (the default for `node:22-alpine` unless overridden).
- **OWASP:** A05:2021 – Security Misconfiguration
- **Severity:** High
- **Fix:** Switch to the built-in non-root `node` user before `CMD`, e.g.:
  ```dockerfile
  USER node
  ```
  (verify file permissions on `/app` still allow read access for that user).

### 7.2 `Dockerfile:11-12, 28-29` — Full `npm ci` (including devDependencies) in the production image
- **Description:** The production stage installs all devDependencies (webpack, ts-loader, typescript, axios, etc.) because `tsx` (a devDependency) is used as the production runtime. This bloats the image and includes build tooling in the runtime container.
- **OWASP:** A05:2021 – Security Misconfiguration (unnecessary attack surface)
- **Severity:** Low-Medium
- **Fix:** Install `tsx` as a production dependency and use `npm ci --omit=dev` for the final stage, or pre-compile server TypeScript to JS in the builder stage and run plain `node` in production.

### 7.3 `Dockerfile` — No `HEALTHCHECK`
- **Severity:** Low
- **Fix:** Add a `HEALTHCHECK` instruction against a lightweight health endpoint (add one if none exists).

### 7.4 `docker-compose.yml:1-8` — No resource limits or restart policy
- **Description:** The `app` service defines no CPU/memory limits, no `restart` policy, and no filesystem hardening (`read_only`, `cap_drop`).
- **Impact:** A runaway process/memory leak has no ceiling, and the container will not automatically restart after a crash.
- **OWASP:** Performance/Reliability / A05:2021
- **Severity:** Medium
- **Fix:**
  ```yaml
  services:
    app:
      build: .
      restart: unless-stopped
      deploy:
        resources:
          limits:
            cpus: "1.0"
            memory: 512M
  ```

### 7.5 `Dockerfile:7,23` — Floating base image tag
- **Description:** `FROM node:22-alpine` is not pinned to a digest, so image contents can change between builds without notice; this is also relevant given `bcrypt` is a native addon sensitive to musl/libc version drift.
- **OWASP:** A08:2021 – Software and Data Integrity Failures
- **Severity:** Low
- **Fix:** Pin to a specific digest (`FROM node:22-alpine@sha256:<digest>`) and manage updates via Dependabot/Renovate.

### Positive findings
- Secrets are injected only via `env_file`/environment variables at runtime, not baked into the image or hardcoded in `Dockerfile`/`docker-compose.yml`. `.env` is present in `.gitignore` and `.dockerignore`.
- `server/config/app.ts:51-53` fails fast at startup in production if `SESSION_SECRET` is unset, rather than silently falling back to a weak default (though note the fallback (`'testtest'`) still exists for non-production runs — acceptable for local dev only).

## 8. CSRF Exposure

### 8.1 `server/config/app.ts:64-69`, `server/routes/auth.ts:91-98` — `sameSite: 'none'` in production with no CSRF token
- **Description:** Session cookies use `sameSite: 'none'` in production (required for the current cross-site cookie flow), but no CSRF-token mechanism was found protecting any state-changing route (`/login`, `/update-profile`, `/resetPassword`, `/createAccount`, and all admin/inventory/POS/vendor POST/DELETE/PATCH routes). `sameSite=none` causes browsers to attach the session cookie on cross-site requests; CORS restricts which origins can *read* the response but does not stop the request from being *sent* and processed.
- **OWASP:** A01:2021 – Broken Access Control (CSRF)
- **Severity:** Medium
- **Fix:** Add CSRF token validation (e.g., double-submit cookie pattern) for all state-changing routes, or restrict `sameSite` to `'lax'`/`'strict'` if the cross-origin cookie requirement can be relaxed.

## 9. Reliability / Error Handling

### 9.1 `server/routes/POS.ts:226-262` — N+1 query pattern in `/update-ticket`
- **Description:** Ticket item deletes/updates/inserts are each executed in a `for` loop issuing one DB round-trip per item, inside an open transaction (`BEGIN` at line 196).
- **Impact:** Multiplies DB round-trips and increases lock hold time for tickets with many line items, raising contention risk under load.
- **OWASP:** Performance/Reliability
- **Severity:** Medium
- **Fix:** Batch these operations using multi-row `INSERT`/`UPDATE ... FROM (VALUES ...)`/`DELETE ... WHERE id = ANY($1)`.

### 9.2 `server/routes/admin.ts:259, 282` — Redundant nested `BEGIN` in `/regenerateAccessToken`
- **Description:** A second `BEGIN` is issued at line 282 while a transaction from line 259 may still be open (only a `COMMIT` at line 279 separates them, but the logic is easy to break on future edits).
- **OWASP:** Performance/Reliability
- **Severity:** Low
- **Fix:** Consolidate into a single transaction spanning both operations, or clearly document/verify the two-transaction design is intentional.

### 9.3 Missing pagination on list endpoints
- **Routes:** `admin.ts` `/getAllAccessTokens`, `/getUsers`, `/getVendors`, `/discounts`, `/sales`; `inventory.ts` `/all`, `/search`.
- **Impact:** These return unbounded result sets; response time/memory usage grows linearly with table size.
- **OWASP:** Performance/Reliability
- **Severity:** Medium
- **Fix:** Add `LIMIT`/`OFFSET` or cursor-based pagination.

### 9.4 `server/config/nodemailer-config.ts`

## Appendix: Positive Security Practices Observed

- All server-side SQL queries reviewed use parameterized queries (`$1, $2, ...`); no string-concatenated SQL/SQL-injection was found anywhere in `server/routes/*` or `server/config/db.ts`.
- Passwords are hashed with `bcrypt` (cost factor 10) both at account creation and password reset; plaintext passwords are never stored.
- Password-reset tokens use `crypto.randomBytes(32)` — cryptographically strong, unlike the numeric account-creation access tokens (see 1.2).
- `requireAuth`/`requireUserType` middleware is well-structured and used correctly wherever it is applied.
- Sessions are stored server-side via `connect-pg-simple` (not the unsafe default `MemoryStore`), with `httpOnly` cookies and environment-driven `SESSION_SECRET` enforcement in production.
- `vendor.ts` and the `/vendor/*` routes in `inventory.ts` correctly scope all queries by the session's `vendorId`, and are a good reference pattern for fixing the IDOR issues found in `admin.ts` and `inventory.ts`'s admin-facing routes.
- `POS.ts` uses `SELECT ... FOR UPDATE` row locking before status-dependent ticket updates/deletes, correctly guarding against race conditions.
- No hardcoded secrets, API keys, or credentials were found in client-side TypeScript, `Dockerfile`, or `docker-compose.yml`; secrets are sourced from environment variables / `.env` (which is correctly excluded via `.gitignore`/`.dockerignore`).
